## TD-01 / TD-02 D1 기준선과 소유권

### 해결 내용

- `packages/db/drizzle-v2`에 9개 canonical migration을 구성했다.
- 기존 migration 파일을 재작성하지 않고 새 canonical chain으로 분리했다.
- 일반 table은 Drizzle schema, FTS virtual table/trigger는 reviewed SQL이 소유한다.
- OAuth runtime DDL을 제거했다.
- transfer allowlist는 23개 보존 대상 일반 table을 포함하고 2개 OAuth state/token table과 FTS를 제외한다.

### 남은 위험

현재 `wrangler.toml` binding은 기존 `nihongo-n3-prod`다. production ledger가 정상화된 것은 아니므로 prod-v2 전환 전에는 `완료`가 아니라 `구현 완료`다. 기존 DB에 migration 이력을 임의 backfill하지 않는다.

### 2026-07-15 Blue/Green 사전 점검

- Cloudflare D1 목록에 `nihongo-n3-prod-v2`가 없어 migration ledger와 content dry-run은 아직 생성할 수 없다.
- GitHub 기본 브랜치에는 구 `Content Update & DB Migration`만 등록돼 있고, R1 브랜치의 승인형 `Content and D1 Change Control`은 아직 UI 실행 대상이 아니다.
- GitHub `production` Environment와 그 Environment secret 이름이 없다.
- 기존 production을 읽기 전용 조회한 결과 `vocab/vocab_fts=3,427`, `sentences/sentences_fts=1,112`였다. fresh 기준 vocab 3,300보다 127건 많고 `categories=0`, `curriculum_weeks=16`이므로, 이전 전에 provenance와 canonical 기준을 결정해야 한다.
- transfer 도구는 dry-run과 실행 전후 count·normalized checksum JSON, FTS 원본 parity와 3,300/1,112 기준 판정을 남기도록 보강했다.
- 2026-07-18 통합 후보의 로컬 fresh DB에서 9/9 migration과 manifest/FTS/FK 검증이 통과했다. 이는 remote prod-v2 완료 증거를 대신하지 않는다.

따라서 TD-01은 `구현 완료`, TD-02는 코드 기준 `검증 완료 / prod-v2 적용 대기`를 유지한다. production D1/R2 쓰기와 binding 변경은 수행하지 않았다.

## TD-05 / TD-07 콘텐츠 계약

- shared JLPT level은 N5~N1을 표현할 수 있다.
- 운영 manifest v2는 실제 존재하는 N5~N3 13개 source만 사용하며, 각 source에 원천·라이선스·검수자·최종 검토일을 강제한다.
- parser는 `의미`, `뜻`, `한국어 뜻`을 인식하고 빈 뜻을 실패시킨다.
- source별 row/checksum·source version·parser version, category, required field, duplicate, FK, FTS parity를 검증한다.
- 각 seed run은 `content_seed_runs` 및 `content_seed_sources`에 content version, manifest SHA-256, source checksum, parser version, provenance를 기록한다.
- N2/N1 WIP는 별도 branch로 격리했다.

### TD-07 provenance와 동음이의어 출시

`packages/db/src/seed/homophone-pairs.ts`에는 출처 mapping, 악센트 reference URL, 일본어·한국어 예문, 검수자와 날짜가 있는 30쌍을 기록했다. migration `0007_content_provenance_homophones.sql`은 이 필드와 seed-run ledger를 추가한다. verifier는 검수 완료 쌍이 30개 이상인지, 불완전 검수 record·동일 읽기 위반·source mapping 위반·unordered duplicate·FK violation이 모두 0인지 확인한다.

공개 `GET /api/v1/homophones`는 조건을 만족하는 쌍만 반환하며, OpenAPI와 Browse의 동음이의어 탭이 같은 release에서 활성화됐다. 로컬 fresh DB에서 canonical migration과 manifest 검증 항목이 통과했다. 따라서 TD-07은 코드·데이터 관문 기준 `검증 완료`다. 이 판정은 production D1/R2 변경이나 N2/N1 콘텐츠 출시를 의미하지 않는다.

N2/N1 타입 확장을 콘텐츠 출시로 오인하지 않는다. 원본 7개와 provenance가 없으면 source mapping에 추가하지 않는다.

후보가 운영 범위에 섞이지 않았음을 `seed:diff`로 재확인했고, 운영 13-source `verify:fresh`는 migration 7/7·FTS 3,300/1,112·FK·필수값·중복 검사를 통과했다. verifier는 각 count query를 별도 Wrangler process로 실행하던 방식을 단일 JSON batch로 바꿨지만, 검사 항목과 기준은 완화하지 않았다. 이 통과는 후보 N2/N1 출시 증거가 아니며 TD-07의 상태를 바꾸지 않는다.

## TD-08 오디오

공개 Worker route의 요청 시 생성은 제거했다. 승인된 R2가 1순위이고 browser Japanese voice가 fallback이다. Google 전체 배치는 관리자 인증, `execute:true`, provider `google`, approval token을 요구한다.

청해 API가 `audio_r2_key IS NULL`인 문장에도 존재하지 않는 legacy 경로를 조합하던 결함을 제거했다. 이제 승인된 DB 키만 응답하며 fresh DB에서는 브라우저 fallback을 사용한다. 오디오 요소도 사용자 재생 전에는 서버 파일을 preload하지 않아 미생성 R2로 인한 페이지 로드 404를 만들지 않는다.

남은 4,954건은 `verify:fresh`에서는 warning이고 `verify:fresh:audio` 재검증에서는 유일한 blocking failure였다. 이를 숨기기 위해 verifier 최소값을 낮추지 않는다.

2026-07-15에는 API·웹이 같은 `audio-qa-30-v1` 표본을 사용하도록 통합하고, 평가자/device/browser/날짜와 후보별 voice/model/version 및 5개 청감 점수를 모두 요구하는 scorecard를 구현했다. queue는 N5→N4→N3 level 승인, Google 전용 secret, 불변 object 무덮어쓰기, provider별 성공/실패 이력을 사용한다. `verify:remote:audio`는 이제 D1 key 형식뿐 아니라 R2 객체의 provider/model/audio version/content hash/item metadata와 immutable cache까지 검증한다.

읽기 전용 원격 확인 결과 Cloudflare QA만 30/30이고 Google 0/30, VOICEVOX 0/30이었다. 두 batch secret도 없으며 기존 production `audio_generation_log`에는 `provider`, `content_hash` 컬럼이 없다. 기존 production 대상 5,085건은 모두 새 불변 key와 불일치했다. 따라서 TD-08은 `검증 완료`로 변경하지 않으며 R1 prod-v2 전환, 네 후보 사람 청감 승인, N5→N3 batch, 누락 0이 순서대로 필요하다.

## TD-13 / TD-14 운영 증명

Workers는 객체형 PII 없는 request/auth/D1 log, release·route template·latency 집계와 100% log sampling을 코드에 설정했다. 실제 path parameter/query와 preview canary secret을 기록하지 않는 회귀 테스트를 포함한다. `scripts/setup-logpush.mjs`, `scripts/setup-alerts.mjs`, `scripts/post-deploy-observe.mjs`는 각각 Logpush job, 세 saved query·배포 상태 확인, 30분/24시간 smoke·집계를 담당한다. API Worker의 5분 Cron은 공통 판정 코어로 세 임계값을 평가해 secret webhook으로 전달한다.

2026-07-15 원격에서 `nihongo-n3-reports/logs/workers/` prefix의 30일 lifecycle `nihongo-n3-worker-logs-30d`를 적용·재조회했다. 새 account-owned API token과 bucket-scoped R2 S3 자격증명을 값 비노출로 검증한 뒤 account-level Logpush job을 생성했고, enabled와 빈 `error_message`를 재확인했다. Workers Observability의 5xx, auth failure, D1 error saved query 세 개도 생성했다.

직접 운영 HTTPS endpoint를 `nihongo-n3-observability-receiver-preview`로 분리하고 sender는 `OBSERVABILITY_ALERT_RECEIVER` service binding을 우선 사용하게 했다. receiver는 bearer 인증, 64 KiB 상한, PII 형태 거부를 거친 집계만 `alerts/observability/YYYY/MM/DD/<sha256>.json`에 저장한다. 같은 Worker의 공개 URL을 다시 호출하던 초기 preview 실패는 별도 receiver와 service binding으로 해소했다.

2026-07-15 preview에 runtime secret을 등록하고 sender `247ff8f7-bdbc-4a29-959e-7055eaaeeb52`, receiver `65110623-59d3-456d-8699-29928a25f48d`를 배포했다. 공개 smoke 7/7, canary 25/25 HTTP 500, 5xx detector 발화, webhook 수신을 통과했다. 08:00 UTC 자동 Cron도 source `worker-cron`, release `4a54d718c58f42aeef2c573d6e3889bc86fad456` 집계를 receiver에 전달했고 R2에 저장됐다. Logpush `.log.gz` 20개와 alert evidence 4개를 metadata 기준 확인했다.

이에 따라 TD-13은 `검증 완료 (preview E2E)`로 변경한다. production Worker는 여전히 이전 배포본이며 변경하지 않았다. production cron·secret·Logpush 활성화는 GitHub required checks와 Environment 승인을 통과한 릴리스에서 같은 검증을 다시 수행해야 한다. preview의 `OBSERVABILITY_API_TOKEN`은 자동 전용 토큰 발급 권한이 없어 기존 account control token을 임시 사용했으므로 production 전 최소권한 전용 토큰으로 교체한다.

GitHub Backup run [29631932489](https://github.com/kordokrip/JLPT/actions/runs/29631932489)는 Environment 승인과 runner 시작 후 D1 export API가 `10000 Authentication error`를 반환해 실패했다. 활성 D1 Read/Write scoped token으로 같은 API를 직접 호출해도 재현됐으므로 billing annotation이나 코드 테스트 실패와 분리했다.

대체 경로 `nihongo-n3-d1-backup-workflow`는 REST export credential을 runtime에 저장하지 않고 D1/R2 binding으로 canonical 일반 table 23개를 export한다. 인스턴스 `manual-backup-2026-07-18T05-36-28-521`이 complete였고, R2 root `backups/workflow/2026-07-18/2026-07-18T05-36-35-908Z`에 SQL 23개와 manifest 2개를 기록했다. manifest SHA-256은 `487870e112bd3e0ad41466848bf25336d4800b3711ee738013a875af5603df43`이다. 내려받은 object의 checksum, migration 9/9, table별 row count, FK, 재구축 FTS parity를 local fresh D1 restore drill로 통과했고 `backups/` prefix에 30일 lifecycle을 확인했다.

따라서 TD-14를 `검증 완료`로 변경한다. 이 판정은 자동 schedule을 허용하지 않는다. binding 기반 table export는 단일 transaction snapshot이 아니므로 승인된 read-only/maintenance 구간의 수동 실행과 매회 restore drill을 계속 요구한다. 상세 근거는 [Cloudflare D1 백업 Workflow](./cloudflare-d1-backup-workflow.md)에 기록했다.
